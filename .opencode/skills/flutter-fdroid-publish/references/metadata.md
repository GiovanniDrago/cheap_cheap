# F-Droid metadata — fields and Flutter build recipes

The file is `metadata/<package-id>.yml` in `fdroiddata`. It is YAML, not XML. The
published index is generated by `fdroid update`; never create it by hand.

## Contents

- Descriptive fields
- Build blocks
- Flutter submodule recipe
- Matching a custom upstream build path
- Flutter srclib fallback
- Update configuration
- New vs update
- Gotchas

Use `assets/metadata-submodule.yml` by default and `assets/metadata-srclib.yml` only as a
fallback. Replace every `__PLACEHOLDER__`; the validation script rejects leftovers.

## Descriptive fields

| Field | Rule |
|---|---|
| `Categories` | A YAML list; use the live list from `references/categories.md` |
| `License` | One SPDX identifier, e.g. `GPL-3.0-only`, `MIT`, `Apache-2.0` |
| `AuthorName` | Public author name or pseudonym; same spelling across the author's apps |
| `SourceCode` | Human-friendly source URL, usually the repository page |
| `IssueTracker` | Issue tracker URL |
| `Changelog` | Release/changelog URL |
| `RepoType` | `git` |
| `Repo` | Public HTTPS clone URL, normally ending in `.git` |

Do **not** add `Summary`, `Description`, `Name`, icons, screenshots, or changelog text to
the metadata. F-Droid reads them from the upstream fastlane tree. Creating them here
overrides the developer's translations and is rejected by the MR checklist.

## Build blocks

Each ABI gets its own build block. For base version code `N`:

| ABI | versionCode | Typical `--target-platform` |
|---|---|---|
| `armeabi-v7a` | `N * 10 + 1` | `android-arm` |
| `arm64-v8a` | `N * 10 + 2` | `android-arm64` |
| `x86_64` | `N * 10 + 3` | `android-x64` |

`CurrentVersionCode` must be the highest value, i.e. the last ABI block.

Required per block:

- `versionName`: the public version, without the `+N` build suffix;
- `versionCode`: the ABI-specific code;
- `commit`: the full 40-character commit hash, not a tag or branch;
- `output`: the APK path produced by Flutter;
- `binary`: the upstream release URL for the same APK, only when the build is
  reproducible (see `references/reproducibility.md`).

Common optional fields:

- `submodules: true` when Flutter or another dependency is a git submodule;
- `subdir`: the directory containing `pubspec.yaml`, if it is not the repository root;
- `rm`: remove unused platforms before scanning;
- `prebuild` / `build`: commands for the Flutter toolchain;
- `scanignore` / `scandelete`: scanner exceptions, with a reason in the MR.

## Flutter submodule recipe

This is the default recommended by the official `templates/build-flutter.yml`.

```yaml
Builds:
  - versionName: 2.0.11
    versionCode: 200111
    commit: 0123456789abcdef0123456789abcdef01234567
    submodules: true
    output: build/app/outputs/flutter-apk/app-armeabi-v7a-direct-release.apk
    binary: https://github.com/example/notes/releases/download/v%v/app-armeabi-v7a-direct-release.apk
    rm:
      - ios
      - linux
      - macos
      - web
      - windows
    prebuild:
      - export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
      - export PUB_CACHE=$(pwd)/.pub-cache
      - .flutter/bin/flutter config --no-analytics
      - .flutter/bin/flutter pub get --enforce-lockfile
    scanignore:
      - .flutter/bin/cache
    scandelete:
      - .flutter
      - .pub-cache
    build:
      - export PUB_CACHE=$(pwd)/.pub-cache
      - .flutter/bin/flutter build apk --release --split-per-abi
        --target-platform="android-arm" --build-name $$VERSION$$
        --build-number $(( $$VERCODE$$ / 10 )) --flavor direct
        --dart-define=DISTRIBUTION_CHANNEL=direct
```

Notes:

- The submodule is normally mounted at `.flutter` in the repository root. If it lives
  elsewhere, change every path and tell the metadata agent.
- `pub get --enforce-lockfile` requires a committed `pubspec.lock`. If the project does
  not commit it, use `pub get` and explain why in the MR.
- `--flavor` and `--dart-define` are optional. If there is no flavor, remove the flag and
  the flavor segment from the APK filename.
- `--target-platform` must match the ABI of the block.
- `scanignore` and `scandelete` are not a way to hide non-free code. They only exclude
  generated caches and toolchain binaries that the scanner cannot classify.

### Matching a custom upstream build path

If the release workflow builds from a fixed absolute path, the recipe must use the same
path. The official template does this with `sudo`, `mv`, and `pushd`:

```yaml
    sudo:
      - mkdir -p /home/vagrant/build/com.example.notes
      - chown -R vagrant /home/vagrant/build
    prebuild:
      - export repo=/home/vagrant/build/com.example.notes
      - cd ..
      - mv com.example.notes $repo
      - pushd $repo
      - export PUB_CACHE=$(pwd)/.pub-cache
      - .flutter/bin/flutter config --no-analytics
      - .flutter/bin/flutter pub get --enforce-lockfile
      - popd
      - mv $repo com.example.notes
    build:
      - export repo=/home/vagrant/build/com.example.notes
      - cd ..
      - mv com.example.notes $repo
      - pushd $repo
      - export PUB_CACHE=$(pwd)/.pub-cache
      - .flutter/bin/flutter build apk --release --split-per-abi ...
      - popd
      - mv $repo com.example.notes
```

Use the same directory name that F-Droid uses for the checkout (`build/<package-id>`).
The `mv` target and the workflow's `REPRO_BUILD_DIR` must match exactly. If the paths
differ, the `binary:` comparison will fail even when the source is identical.

## Flutter srclib fallback

Use this only when the user does not want a Flutter submodule.

```yaml
    srclibs:
      - flutter@stable
    prebuild:
      - "flutterVersion=$(sed -n -E \"s/.*flutter-version: '(.*)'/\\1/p\" .github/workflows/release.yml)"
      - '[[ $flutterVersion ]]'
      - git -C $$flutter$$ checkout -f $flutterVersion
      - export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
      - export PUB_CACHE=$(pwd)/.pub-cache
      - $$flutter$$/bin/flutter config --no-analytics
      - $$flutter$$/bin/flutter pub get --enforce-lockfile
    scandelete:
      - .pub-cache
    build:
      - export PUB_CACHE=$(pwd)/.pub-cache
      - $$flutter$$/bin/flutter build apk --release --split-per-abi
        --target-platform="android-arm" --build-name $$VERSION$$
        --build-number $(( $$VERCODE$$ / 10 )) --flavor direct
        --dart-define=DISTRIBUTION_CHANNEL=direct
```

The workflow file must contain a `flutter-version: 'x.y.z'` line. If the version is pinned
elsewhere, change the extraction command.

## Update configuration

```yaml
AutoUpdateMode: Version
UpdateCheckMode: Tags ^v[\d.]+$
VercodeOperation:
  - '%c * 10 + 1'
  - '%c * 10 + 2'
  - '%c * 10 + 3'
UpdateCheckData: pubspec.yaml|version:\s.+\+(\d+)|.|version:\s(.+)\+
CurrentVersion: 2.0.11
CurrentVersionCode: 200113
```

- `AutoUpdateMode: Version` with `UpdateCheckMode: Tags` lets F-Droid create the next
  build blocks from a tag.
- `UpdateCheckData` extracts the base code from `pubspec.yaml` (`version: x.y.z+N`) and the
  version name from the same file.
- If the project does not use `+N`, do not copy this line: derive the code from
  `build.gradle` or the tag and document the extraction.
- `VercodeOperation` must have exactly one entry per build block.
- `CurrentVersionCode` must be the highest ABI-specific value.

## New vs update

For `new`:

1. create `metadata/<package-id>.yml`;
2. fill the descriptive fields and the three build blocks;
3. run the validation loop.

For `update`:

1. read the current file from `fdroiddata` `master`;
2. preserve `Categories`, `License`, `AuthorName`, `SourceCode`, `IssueTracker`,
   `Changelog`, `RepoType`, `Repo`, and any translator/maintainer notes;
3. replace the `Builds` list with the new release only;
4. update `CurrentVersion` and `CurrentVersionCode`;
5. keep `AutoUpdateMode`, `UpdateCheckMode`, `UpdateCheckData`, and `VercodeOperation`
   unless the upstream release process changed;
6. do not add a second app, images, descriptions, or disabled versions.

If the package ID changed, treat it as a new app, not an update.

## Gotchas

- `binary:` must be a single URL; if `rewritemeta` wraps it, keep the exact output.
- The Flutter APK filename is `app-<abi>-<flavor>-release.apk`; the order is ABI first.
- `CurrentVersionCode` is the highest ABI code, not the base code.
- `commit:` must be 40 hex characters and must exist on the upstream remote.
- `AllowedAPKSigningKeys` is the lowercase SHA-256 of the signing certificate, not the
  APK checksum.
- Do not add `binaries:` at the top level unless the app has no build recipe; a build
  recipe uses per-build `binary:`.
- `Repo` uses the clone URL; `SourceCode` uses the human page.
- Run `fdroid rewritemeta` and apply its exact diff instead of guessing line wrapping.
